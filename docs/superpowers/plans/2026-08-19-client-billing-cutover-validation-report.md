## Summary — for a non-technical reader (Finance / sign-off)

**8,050 of 10,797 historical invoice rows (74.6%) are ready to load as-is.
0 of 144 historical credit-note rows are ready to load yet.** The remaining
2,747 invoice rows and all 144 credit-note rows need one of the decisions
below before the load step (a separate, later, explicitly-gated task) can
run. None of this blocks anything already live — this is a dry run only; the
real `client_invoice`/`client_credit_note` tables are untouched (still 0 rows,
confirmed below) and nothing on the production system reads this staging
data.

The credit-note number is 0% not because the data is bad, but because **the
new schema has no column that can record which invoice a historical credit
note belongs to**, and the legacy system never recorded that link reliably
either — this is a real design gap that needs a decision, not a data-quality
problem Finance needs to chase down. See "Credit-note findings" below.

## 2. PREPARE-verification against the live schema

Before touching row-level data, this task PREPAREd (never EXECUTEd) a real
`INSERT` statement shaped like Task 4's eventual load, against the live
`client_invoice`/`client_credit_note` tables:

```
client_invoice: PREPARE compiled cleanly against the live schema (20-column shape)
client_credit_note: PREPARE compiled cleanly against the live schema (20-column shape)
```

Both PREPAREs compiled successfully — there is no column-name or
column-count mismatch. The real problems this task found are **data-level**
(a required `NOT NULL` column with no reliable source value on some or all
rows), not SQL-shape problems. Specifically, re-reading `client_invoice`'s
and `client_credit_note`'s live `information_schema.COLUMNS` (not assumed
from the design doc) surfaced three things the design doc did not
anticipate:

1. **`client_invoice.gst_type` / `client_credit_note.gst_type` are
   `VARCHAR(20) NOT NULL` with no `DEFAULT`.** Design §5.2 calls for
   migrating GST-blank rows with `gst_type = NULL` — that is not insertable
   against the live schema as it stands. This is the single largest error
   cause (2,229 invoice rows, all 144 credit-note rows).
2. **`client_invoice.category` / `client_credit_note.category` are
   `VARCHAR(50) NOT NULL`.** `normalizeCategory()` (Task 2's own transform,
   correctly per its own design intent) returns `NULL` for blank/NULL legacy
   category rather than inventing a bucket — but that NULL is not insertable
   either (510 invoice rows, 1 credit-note row).
3. **`client_invoice.cost_centre_id` / `client_credit_note.cost_centre_id`
   are `CHAR(36) NOT NULL` FKs to `cost_centre_master.id`.** Neither the
   design doc, migration 1304/1305, nor `extract.ts` computed any mapping
   for this column at all — it does not exist anywhere in the staging table
   or in any prior task's output. This task resolves it for the first time,
   by joining the legacy free-text `src_cost_center` against
   `cost_centre_master.cost_centre_code`: **10,710 of 10,797 invoice rows
   (99.2%) and all 144 credit-note rows match cleanly.** Only 87 invoice
   rows (85 with an unrecognized code + 2 with a blank `cost_center`) fail
   to resolve — see the breakdown below for the specific unmatched codes.
4. **`client_credit_note.invoice_id` is `CHAR(36) NOT NULL` with a real FK
   constraint to `client_invoice.id`** — see "Credit-note findings" below.
   This is the dominant reason all 144 credit-note rows currently fail.

`created_by` (`CHAR(36) NOT NULL` on both tables) has **no FK constraint**
(confirmed via `information_schema.KEY_COLUMN_USAGE`), so it is a
policy decision (which placeholder/system actor UUID to use for a migrated
row), not a per-row blocker — it does not appear in the error counts below
because any fixed value satisfies it.

## 4. `bill_no` / `credit_no` collision groups

- **Invoices**: **2,001 distinct `bill_no` values** are shared by more than
  one row, covering **4,005 individual rows** (of 10,797, i.e. 37.1%). This
  is close to design §2's own count (2,010 numbers / 4,023 rows) — the small
  difference is because this count is taken after Task 2's own `status=1`
  exclusion and blank-`bill_no` filtering, not against the raw
  `tbl_invoice` table design §2 queried.
- **Credit notes**: **22 distinct `credit_no` values** are shared by more
  than one row, covering **104 of 144 rows (72.2%)**. The worst is
  `17-06/22-23`, reused by 25 different credit notes (`legacy_id`s 17, 21,
  23–45) — confirms design §2's finding exactly.

**Every group with its full `legacy_id` list is in Appendix A (invoices) and
Appendix B (credit notes) below** — Appendix A alone is 2,001 rows, so it is
collapsed behind a `<details>` toggle to keep this report readable; every
row is real query output, not a sample.

No row is currently marked `error` because of a collision — per design §5.3,
a colliding `bill_no`/`credit_no` is preserved as historical fact, not
treated as a load blocker, since `legacy_id` (not the human-readable number)
is what disambiguates the row in the new schema.

## 5. GST-type-null row count (re-confirmed)

- **Invoices: 2,229 of 10,797 rows (20.6%)** have `target_gst_type = NULL`
  (i.e., legacy `GSTType` was blank/NULL). Task 2's own extraction run
  reported the same figure. Design §2's headline number (2,237 of 11,031,
  ~19.7%) was taken before the `status=1` exclusion and against the full
  11,335-row table; 2,229/10,797 is the correct figure for what actually
  landed in staging.
- **Credit notes: 144 of 144 rows (100%)** have `target_gst_type = NULL` —
  every single legacy credit note has a blank `GSTType`. This is a new
  finding beyond what design §2 covered (design §2's GST-null figure was
  computed only against `tbl_invoice`).

## 6. Credit-note `status`/`credit_approve` investigation and recommendation

Task 2 deliberately did not exclude any `tbl_credit_note` rows on `status`,
flagging the decision as this task's to make. Re-querying the live staging
data (which itself came from a fresh `db_bill` read) confirms Task 2's own
finding and lets this task make the call with real numbers:

| `src_status` | `src_credit_approve` | Row count | createdate range |
|---|---|---|---|
| 1 | 1 | 121 | 2024-06-17 → 2026-08-18 (includes the 5 most recent credit notes in the whole table) |
| 1 | 0 | 17 | overlaps the above range |
| 0 | 0 | 6 | 2024-08-16 → 2026-04-22 (all unapproved) |

**Recommendation: do not exclude any `tbl_credit_note` row on `status`.**
`tbl_invoice.status=1` means legacy's own "deleted" flag (confirmed:
excluding it there removes 234 genuinely void invoices). `tbl_credit_note`'s
`status` column measures something entirely different — it correlates with
`credit_approve` and with recency, not with deletion, and there is no
`InvoiceDeleteRemarks`-equivalent "this one is void" signal anywhere on
`tbl_credit_note`. Applying `tbl_invoice`'s rule here would keep only the 6
`status=0` rows and silently drop 138 real, live credit notes (96% of the
table) — clearly wrong. All 144 rows should proceed to the load step once
the structural blockers below are resolved; `credit_status` (the new
schema's own enum, `'draft'`/`'approved'`) should be set from
`credit_approve` (1 → `'approved'`, else → `'draft'`), not from `status`,
since `credit_approve` is the field that actually means what the new
column's name says.

## 7. The credit-note `invoice_id` structural gap (new finding, blocks 100% of credit notes)

`client_credit_note.invoice_id` is `CHAR(36) NOT NULL` with a real foreign
key to `client_invoice.id` (confirmed live via
`information_schema.KEY_COLUMN_USAGE`). Re-inspecting
`db_bill.tbl_credit_note`'s live column list (39 columns) directly: **there
is no column on `tbl_credit_note` that reliably identifies which
`tbl_invoice` row it was issued against.** `proforma_bill_no` exists on both
tables and looks like the obvious join key, but given §4's collision
finding (`bill_no`/`proforma_bill_no` are reused by design/bug across
thousands of legacy rows), a `proforma_bill_no` string match would
frequently attach a migrated credit note to the *wrong* migrated invoice —
silently, with no way to detect it later. That is worse than refusing to
load the row. **This is why all 144 credit-note rows currently fail
validation regardless of any other data-quality issue**, and it is a design
gap, not a per-row data problem: neither the design doc, nor migrations
1304/1305, nor Task 2's extraction defined any linking strategy for this
column. It needs one of:

- a human/Finance-assisted manual mapping for the ~40 distinct
  `proforma_bill_no`/date/amount combinations actually in play (144 rows,
  not thousands — tractable by hand), or
- loading credit notes only after their corresponding invoices are migrated
  and re-deriving the link from a best-effort match on `proforma_bill_no` +
  `cost_center` + amount, with every ambiguous case (any `bill_no` collision
  group) flagged for manual review rather than auto-linked, or
- a decision that historical credit notes migrate without a real
  `invoice_id` link (e.g., a schema change making the column nullable for
  `is_migrated=1` rows) — a schema decision outside this task's scope to
  make unilaterally.

This is the single most consequential open decision from this validation
pass and needs explicit sign-off before Task 4 can do anything useful with
credit notes.
