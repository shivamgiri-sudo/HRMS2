# KPI Catalogue — one source of truth for every process KPI

Date: 2026-10-01. Status: approved by the owner (option 1, KPI Studio fully synced).

## Problem

Six models define KPIs independently and resolve targets in different orders: `kpi_template`/`kpi_assignment`
(legacy), `kpi_master_config` (My KPI), `kpi_process_config`, role templates (`kpi_role_template*`),
`kpi_studio_definition`, and `portal_kpi_config`. Two rating scales disagree (S/A/B/C/D in `kpi_rating_config`
vs Outstanding/Exceeds/Meets in `ratingForScore`). `kpi_master_config.weightage` defaults to 100 per metric and
is never normalised. The client-process registry (`kpi-metric-registry.ts`) is hard-coded for a handful of
processes, and most of the per-process dashboards compute metrics that no KPI model knows about.

## Goal

A single catalogue that says, for each process: which KPIs exist, how each is computed, where its data comes
from, how fresh it is, what its target is, and which role / department sees or manages it. KPI Studio and every
older model are reconciled to it. The employee live-performance page and trends view (P4, separate spec) read
only the catalogue.

## Data model (new tables; no existing table is altered destructively)

- `kpi_rating_scale` / `kpi_rating_scale_band` — one scale for the app. Seeded S/A/B/C/D (100/90/75/60/0).
- `kpi_catalogue` — one row per (process_key, metric_key): name, family, unit, direction, grain
  (`employee|process|both`), source_kind (`dialer_live|upload|daily_sync|studio|derived|manual`), source_ref
  (table / feed), formula, freshness (`realtime|hourly|daily|upload`), dimensions (JSON list), target_source,
  default_target, rating_scale_id, status (`draft|published|retired`), `legacy_refs` (JSON), `studio_definition_id`.
- `kpi_catalogue_role` — (catalogue_id, role_key, department_key, access `view|manage`, display_order, weight).
- `kpi_catalogue_conflict` — reconciliation log: type, process_key, metric_key, detail JSON, resolved flag.

`process_key` is a stable key (the TPZ company key / process_master code), not a process_master id, so the
catalogue seeds without depending on live row ids; `process_id` is resolved at read time.

## Seed (the per-process, per-role KPI map)

`backend/src/modules/kpi-catalogue/kpi-catalogue.seed.ts` is the reviewable map: every KPI the existing
dashboards compute (Process Performance V2, call master, process-operations, process-dashboard, live dashboards,
ops-command) with its real formula, source and refresh class, plus role/department visibility. A Markdown view of
the same data is generated by a script. Metrics with no data feed are marked `source_kind: manual|upload` and
`has_data: false` — never shown as zero.

## Resolution rule (one order)

Target and weight for an employee: employee override > role + process > process > department > designation
default. Effective-dated. Weights are normalised to 100 per employee/process at read time.
Implemented once in `kpi-catalogue.resolve.ts`; old models stay readable through compatibility readers.

## Studio sync

- `kpi_studio_definition.catalogue_id` links a definition to its catalogue row.
- Studio create/edit writes the catalogue row first (draft), then publishes; Studio compute reads formula and
  source from the catalogue row.
- Drift check (`GET /api/kpi-catalogue/drift` + nightly job) compares catalogue vs Studio vs
  `kpi_master_config` / `kpi_process_config` / role templates and records differences in `kpi_catalogue_conflict`.
- Results continue to land in `kpi_daily_actual` / `process_metric_actual`; My KPI and scorecards keep working.

## API

- `GET /api/kpi-catalogue/processes`
- `GET /api/kpi-catalogue/process/:processKey?role=&department=` — KPIs visible to a role.
- `GET /api/kpi-catalogue/conflicts`, `GET /api/kpi-catalogue/drift`
- `POST /api/kpi-catalogue/sync` (admin) — seeds / re-seeds from `kpi-catalogue.seed.ts`, idempotent.
Access is role-gated; per-process reads go through the existing process scope (`readableProcessIds`).

## Phases

P1 map + conflict report (read-only) · P2 tables, seed, read API · P3 Studio sync + drift check ·
P4 live performance page and trends (own spec).

## Non-goals

No destructive migration of existing KPI tables; no change to payroll scoring; no new data pipelines.
